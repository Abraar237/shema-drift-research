The schema changed and nobody told the agent

Tool schemas version: fields get renamed, enums tighten, defaults flip. We measured what breaks when the agent still believes the old schema, how much of it breaks silently, and what a 28-token diff repairs.

Mohammed Abraar · Vizuara Research · abraar@vizz.vizuara.ai

The three-minute version

An agent runs on a copy of someone else's interface

A tool-calling agent carries a schema in its prompt: parameter names, types, enums, required flags, documented defaults. The service behind the tool enforces its own copy. In deployment the two copies drift apart, because services version their APIs on their own schedule. Recent benchmarks established that agents degrade when tool interfaces evolve. What they did not answer is the part a practitioner needs most: when a drifted call fails, does anyone find out, and what is the cheapest fix?

We froze SchemaDrift-120 before applying any drift: 30 tools, 120 tasks whose correct calls a script can check, and five deterministic, single-edit drift classes, so every failure is attributable to a known cause. A local executor enforces the new schema under two tolerance policies (strict and lenient), and every drifted call lands in a three-way ledger: error surfaced, accepted correct, or accepted with wrong semantics.

Which drift is silent is a property of the class times the API's tolerance

Under a strict validator, renames, enum changes, newly required parameters, and type changes all raise errors. Default changes never do: nothing is structurally wrong with the call, so 38 to 46 percent of them execute with wrong semantics even under strict validation. A lenient gateway, the kind that drops unknown fields and coerces types, converts renames (100 percent) and type changes (67 to 79 percent) into silently wrong calls too.

The outcome ledger for Gemini Flash, 48 drifted calls per class. Blue: error surfaced. Magenta: accepted with wrong semantics. Green: accepted correct.

We hand-audited 24 of the accepted-wrong calls, stratified over families and classes. All 24 are genuinely wrong. A few of them:

$80.00 sent as €80
currency default changed USD → EUR; the call violates nothing a validator checks
$2,500 invoiced as $250,000
integer cents met a decimal-string type change; lenient coercion accepted the raw digits
2-day access grant became 4 months
minutes-to-hours type drift, coerced: 2,880 "hours" instead of 48
Toronto job posted as "remote"
renamed location field silently dropped; the new default filled in

A retry loop can only fix what errors. On the drift class that never errors, the raw-error retry recovers exactly nothing.

A 28-token diff repairs Gemini almost fully, and beats the full schema

We compared three recovery levers under identical drift: a structured machine-readable diff of the change, the full new schema, and one retry on the raw error. On both Gemini models the diff recovers 96 to 98 percent of the lost success, at 13.7 percent of the schema's token size, and it outperforms re-injecting the full new schema (82 to 83 percent). The mechanism: when an optional parameter becomes required, its default is deleted from the new schema; the diff carries the old contract, so the agent knows both that the field is now mandatory and which value preserves the old behavior.

Left: success by condition. Right: recovery fraction per lever with bootstrap 95 percent intervals.

And then the other half of the result: the same diff recovers nothing on Qwen2.5-7B (0.06) and nothing on GPT-5.6-luna (point estimate −0.06). Transcripts show both models keep emitting old-schema calls with the change log sitting in the system prompt. The cheapest repair in the study only works for model families that actually read it.

Calling style buys mechanical immunity

GPT-5.6-luna loses only 55 points where Gemini Pro loses 87. Not adaptive robustness: luna fills every optional parameter explicitly in its baseline calls (Gemini models: 45 to 46 percent). A model that always writes currency="USD" itself cannot be hurt when the default changes, and cannot omit a newly required parameter. Its survival on those two classes is 96 percent, versus 25 to 31 percent for Gemini; on the three classes defensive filling cannot help, every family is equally destroyed.

New here: the deterministic minimal-pair drift taxonomy, the error-surfaced versus accepted-wrong ledger conditional on drift class and executor policy, the controlled diff versus full-schema versus retry comparison, and the calling-style exposure axis.

The practitioner reading

Version bumps should ship machine-readable diffs: for families that apply them, drift becomes nearly free to fix at a seventh of the token cost of re-serving schemas. Error-rate monitoring does not cover default changes; the accepted-wrong cell needs its own monitoring. And both the benefit of the diff and the exposure to drift are properties of the model family, so they belong in the evaluation you run before choosing one.
